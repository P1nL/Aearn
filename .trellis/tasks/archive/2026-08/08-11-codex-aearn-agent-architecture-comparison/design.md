# 技术设计

## 设计目标

建立一套可重复、可审计的 Codex 与 Aearn Agent 架构对比方法，使最终结论能够从固定 revision、当前工作树、官方公开行为和真实运行证据反向追溯，而不是依赖功能印象、文件数量或品牌判断。

## 对比单位

以“能力闭环”而不是单个类、文件或 API 为最小对比单位。每个能力闭环至少检查：

1. 输入和状态来源。
2. 核心控制流与不变量。
3. 工具或外部副作用边界。
4. 成功、失败、取消和超时行为。
5. 持久化、恢复和重放方式。
6. 用户可见反馈、trace 和评测覆盖。
7. 源码、测试、文档或运行时证据。

两个项目采用不同领域模型时，不强求类名或模块一一对应，而比较它们是否解决了同一运行时问题。

## 证据规则

使用 `research/baseline.md` 定义的 A-E 五级证据，并遵循以下约束：

- 关键“已实现”判断必须有 A、C 或 D 级证据。
- 官方手册能证明公开产品行为，但不能自动证明开源 runtime 内部实现。
- 测试存在但生产路径未接通时，状态标为“仅测试可用”或“运行时未接通”。
- PRD、设计文档、TODO 和未使用代码只标为“规划中”。
- Aearn 文档与当前代码冲突时，以当前可执行代码和运行证据为准，并记录文档漂移。
- Codex 开源源码与官方手册冲突时，分开陈述 revision 内源码事实与当前公开产品行为，不做无证据合并。

## 实现状态枚举

| 状态 | 判定口径 |
| --- | --- |
| 已实现 | 当前主运行路径已接通，并存在直接源码证据；关键路径有测试或运行证据 |
| 部分实现 | 只覆盖部分路径、边界或异常场景，尚不能形成稳定闭环 |
| 仅测试可用 | 有测试 fixture、prototype 或 isolated implementation，但生产组合根未使用 |
| 运行时未接通 | 代码存在，但未从当前正式入口到达或未被当前配置启用 |
| 规划中 | 只有规格、任务或设计证据 |
| 完全缺失 | 未找到能解决该问题的当前机制 |

| 4 | 工具定义、发现、调用、结果反馈与恢复 | 14 |
| 5 | 工作区、文件系统、Git、shell、浏览器、MCP 与外部环境 | 10 |

上下文、工具和记忆合计占 `42%`，体现本次评估重点；安全、恢复与执行循环继续保持足够权重，避免把“智能”误判为提示词或功能数量。

## 评分标尺

每个维度按 `0-5` 分评分，再乘权重计算总分：

| 分数 | 含义 |
| ---: | --- |
| 0 | 完全缺失，或没有可验证证据 |
| 1 | 只有设计、样例、测试孤岛或不可达代码 |
| 2 | 部分实现，但关键闭环、异常路径或生产接线明显缺失 |
| 3 | 当前可用且边界明确，但可靠性、恢复、规模或治理仍有限 |
| 4 | 机制成熟，主要异常路径、恢复、审计和测试较完整 |
| 5 | 参考级闭环：明确不变量、受控副作用、可靠恢复、可观测和系统评测相互支撑 |

评分不是“Codex 固定为 5”。Codex 与 Aearn 均按相同标尺评分；若 Codex 固定 revision 存在缺口，同样扣分。

## 双层结论

最终报告同时给出两种视角：

1. **通用 Agent Runtime 成熟度**：比较控制循环、上下文、工具、安全、恢复、可观测和治理。
2. **Aearn 教学领域适配度**：评估结构化学习状态、教学决策、练习执行、mastery evidence 和长期学习连续性。

Codex 可作为 coding-agent runtime 的重要参考，但不会因通用工作区能力强而自动在教学领域适配上得高分；Aearn 也不会因领域模型丰富而掩盖 runtime 闭环缺口。

## 上下文专项方法

上下文维度需要逐条追踪：

- 当前用户输入是否始终保留。
- 历史消息的选择顺序、条数、token budget 和优先级。
- system/developer/project instructions 的装载与覆盖。
- tool call、tool result、reasoning item 和外部上下文如何进入后续回合。
- compaction/summary 是调用前还是调用后触发，替换还是追加，失败时如何降级。
- resume/fork/replay 时如何重建上下文并保持不变量。
- 结构化状态是否能避免关键 intake 字段仅依赖聊天历史。
- 是否有超预算、截断、摘要丢失和重复提问回归测试。

重复询问每周时间预算的真实样本作为强制 case study，不允许只用静态源码推测。

## 工具专项方法

工具维度需要区分：

- registry/schema 与动态发现。
- trusted tool、external tool、MCP tool 和 plugin tool 的来源边界。
- 串行/并行调用策略和取消语义。
- 参数校验、权限请求、sandbox、超时、输出截断和错误分类。
- 工具结果如何回灌模型，以及是否保留足够元数据用于恢复和审计。
- 文件读取、搜索、patch、shell、Git、浏览器、MCP/connector 的实际覆盖。
- 执行后是否存在 verify/recover loop，而不是把一次工具返回视为完成。

## 记忆专项方法

记忆维度分为四层，不混为一谈：

1. 当前回合工作状态。
2. 会话历史与 compaction summary。
3. 跨会话 recall memory、项目规则和用户偏好。
4. Aearn 的结构化 learner state、LearningTrack、mastery evidence 等领域真相。

重点检查写入触发、读取资格、污染防护、冲突处理、删除/重置、可解释性和失败恢复。`AGENTS.md`、项目文档和结构化数据库不是同一种 memory，最终报告必须分别评价。

## 产出结构

正式执行阶段计划产生：

- `research/codex-baseline.md`：Codex 固定 revision 的机制与证据。
- `research/aearn-baseline.md`：Aearn 当前工作树的机制、接线和运行证据。
- `research/comparison-matrix.md`：十一维逐项矩阵、状态和评分。
- `research/final-assessment.md`：总体定位、关键风险、近期/中期/长期路线图。

## 质量门

- 每个维度必须至少列出一条 Codex 与一条 Aearn 证据；若无证据，明确写“未找到”。
- 评分必须能从矩阵逐项复算，权重总和必须为 `100`。
- 所有源码引用绑定到固定 commit 或已记录的 Aearn 工作树快照。
- 结论必须区分事实、推断和建议。
- 正式报告完成前，不修改产品代码，不创建实现 child，不提交或部署。
