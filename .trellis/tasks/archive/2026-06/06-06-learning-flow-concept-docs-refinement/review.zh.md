# 学习流程概念检验与官方文档面板 Review

## 你需要审核的结论

这个任务不是重做学习页，而是收紧当前学习流程里的两个高影响体验问题：

- 右侧文档从 Agent 压缩讲义改为可信官方资料区。
- 概念检验从反复追问和大卡片反馈改为少量高价值判断，避免模型泄露答案后要求用户复述。

## 目标

让用户进入知识点后先看到可追溯的官方文档内容和实例，再通过明确边界的概念判断进入代码练习。判断反馈应该轻量、可执行，不制造“模型已经给出答案，用户只需复读”的假学习闭环。

## 范围

- 右侧文档面板只保留两个主区块：`官方文档内容` 和 `实例`。
- 官方文档内容来自官方/可信来源的目标片段，翻译成用户界面语言；不做 AI 压缩、改写或五段式重组。
- 实例区必须区分 `官方示例` 与 `Aearn 示例`。
- `show_concept_check_result` 后端事件继续存在，但前端不再渲染成独立大卡。
- `unclear` 只用于无法判断用户立场的情况；部分正确、漏选或方向明确但不完整应按 `incorrect` / incomplete feedback 处理。
- `incorrect` 和 `unclear` 都计入概念追问轮数；达到上限后进入引导练习、再看例子或跳过概念检验。
- 同一轮输出不得一边泄露目标答案，一边要求用户复述该答案。

## 不做

- 不做整站多语言系统。
- 不做全文官方文档镜像或通用网页翻译器。
- 不改变 FSRS、复习调度、练习评分和提交结果计算。
- 不重构 onboarding 动态路线生成。
- 不删除后端 `show_concept_check_result` tool event，只调整展示和判断策略。

## 关键取舍

- 保留 `show_concept_check_result` 作为持久化事实，降低恢复历史和状态机兼容风险；只改前端展示形态。
- `unclear` 不新增公开枚举，优先把 incomplete 情况表达为 `incorrect` 的解释和下一步，避免 API 变更过大。
- 答案泄露防护不做后端写死兜底；通过 Agent 自检输出契约和测试约束，让模型自己修正下一步问题。
- 官方文档翻译必须保留来源和原文入口，避免把 Aearn 生成内容伪装成官方内容。

## 验收

- 右侧文档面板只出现 `官方文档内容` 与 `实例` 两个主区块。
- 文档区展示来源标题、URL、时间和原文入口。
- 示例区能看出哪些是官方示例，哪些是 Aearn 示例。
- 概念判断结果不再以大卡片形式占据聊天流。
- 判断反馈仍能看到判断、原因和下一步。
- 部分正确或漏答不再被判成 `unclear`。
- `incorrect` / `unclear` 达到追问上限后不再继续“更具体一点”。
- `docs/product/frontend-interaction-spec.md`、`docs/architecture/api-contract.md` 和 `docs/qa/acceptance-test-plan.md` 与实现一致。

## 实施顺序

1. 先更新产品/API/QA 文档，把两段式官方文档面板和概念检验规则固化。
2. 后端调整文档 payload，返回两个主区块并保留来源归因。
3. 后端收紧 concept judgement prompt、`unclear` 边界和追问上限，并保留 Agent 自检 metadata。
4. 前端把判断结果大卡改为紧凑反馈。
5. 前端把文档面板渲染改为官方文档内容 + 实例。
6. 运行 focused backend tests 和 `pnpm --dir .\aearn desktop:check`。

## 风险

- 官方文档片段选择和翻译如果过宽，会带来版权和缓存风险。
- 不做后端写死 guard 后，答案泄露主要依赖 Agent 自检契约；需要用测试和人工验收持续观察模型是否稳定遵守。
- 前端历史消息重放如果仍按旧卡片渲染，会导致新旧体验不一致。
- 当前工作树已有未提交改动，实施时必须避免覆盖用户或其他任务改动。
