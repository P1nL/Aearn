### 建议的 D 最小合同（规划而非现行实现）

1. `resolve_evidence(draft_identity, node_identity, demand, purpose, retrieval_coordinates)` 内部显式开关：仅接受服务器校验的草案 id/version/content hash、node id/目标 hash、canonical Subject/version/facets、exact demand hash；从现有 active corpus + validated summary + C `SourceReviewRepository` 重验授权，按确切 document/revision/hash、chunk id/hash、facet coverage、检索 policy、corpus id/generation/summary、review/admission/政策代次、claim method/receipt（如需）生成**提案**。模型 handle/URL/recommendation 本身不构成事实。selection sufficient/gap 与 exact binding 分开；只在 source/用途/适读性/覆盖/前置条件都满足后标 ready。返回缺口不删目标。
2. `check_current_authorization(binding, purpose, conn, now)`：严格重验绑定全对象、当前开关/actor/demand、同一 `conn` 的 active pointer、corpus summary/validation、link→review→admission→capture/retain→policy/grant/root、approved excerpt 成员及 chunk hash；registered/candidate 分派复用 `_resolve_scoped` + `_verified` 和 `check_source`。对于 assessment 再要求 **exact claim**、独立异族佐证或真实执行 receipt，走 `review_claim`/`authorize_assessment_claim`；目前 C 实际片段仅 `supplementary_explanation`，无 assessment 端到端 authority 时拒绝。
3. `freeze_binding` 不直接信任候选/先前报告：服务端重验草案最新 revision/content hash、session/user/node/目标、subject/registry、selected handle/用途/current pointer/current authorization，然后将这些坐标、coverage/retrieval digest、政策/receipt/claim 坐标写为不可变版本化冻结行。异步回调带 expected draft revision/goal hash；旧回调只能报告 stale，不改历史 active plan。
4. `assert_publication_fence(conn, exact_binding, item_claims, expected_generation, now) -> bounded AuthorizationReceipt`：必须调用方**已经开启同一个短 PostgreSQL 写事务**、相同连接；禁止本函数提交、另连/TTL/缓存或网络 I/O。返回 receipt 含 binding digest、draft/node/goal、corpus/summary/generation、policy/admission/claim 坐标与 fence policy version；题库 owner 在同事务保存到自己的 publication/materialization 行。函数为纯授权断言，不代写题库，也不宣称防止撤权后持续供题；供题要再核验。

### 新表与锁的最小方案、风险

- **最少一张新的不可变 `rag_evidence_bindings`（或 D 专属同义名）**：UUID、draft FK `(draft_id,session_id,user_id)`、draft version/content hash、node/goal/demand hash、用途、Subject/version/facets、corpus FK/id+pointer generation+summary、source/doc revision/hash、chunk id/hash 与 coverage/retrieval digest、review/admission/claim receipt 坐标、binding digest、created_at；唯一 `(draft_id,node_id,goal_hash,purpose,binding_digest)`/明确重试键，CHECK 长度与用途，UPDATE/DELETE 审计拒绝。若真实 draft freeze 数据由另一个不可变已有表明确承载全套坐标且 owner 合同完整，可免建表；目前 `source_summary_json` 不满足，不建议复用为权限表。**不新增** source/corpus/pointer/claim 审核表；题库 publication receipt 写入其 owner 表，D 不建第二 publication ledger。需求/反馈若仅内部短期投影可不建表。
- **旧 writer 必须共用的序列化边界**：`CorpusRepository.activate/rollback` 的 `corpus:pointer:<subject>` exclusive advisory CAS + active row UPDATE；D read fence 对非空 pointer 采用 `FOR SHARE` 并在等待后再次核对 generation/activation event（若需处理空指针竞争，则同 key shared advisory 或直接 fail closed，不把无行 SELECT 当锁）。`rag_source_admissions` 撤权 UPDATE 与 `SourceReviewRepository._resolve_scoped` 的 `FOR SHARE OF r,a` 冲突；registered policy / capture retention clear / candidate access policy / `rag_candidate_use_grants` / rules / root 变更必须与 `_capture`、`PostgresCandidateGrantResolver.resolve` 对应 `FOR SHARE` 串行。不可把仅锁 pointer 当成授权锁，也不可把在另一连接预读的 receipt 当 fence。
- 以现有 C 调用顺序为基线：先锁 exact corpus version（`_verified`），再 link/doc/review/admission，再 capture/policy/grant/root（按现有 `_resolve_scoped`/grant port 顺序），最后锁并重读 active pointer；**避免先拿 pointer 后拿 version**（activate/rollback 由 `_verified` 先锁 version 再进入 pointer CAS）。多 source 固定排序并在生产实现前用双会话竞态/死锁测试锁定顺序。现有 D 之外的直接 `CorpusRepository` 指针 writer 未自动校验 C 授权：D fence 每次独立重验，E 发布前须审计谁能调用 direct writer；不要声称全局统一事务锁已完成。PostgreSQL READ COMMITTED 下锁等待后重新 SELECT current 行，不用预锁快照；时间截止在最后 fence 再取 DB clock，事务长时间跨 expiry 必须失败。revocation 多行 writer 的全局锁排序仍需实测/审计，不可从当前 `FOR SHARE` 推出已经安全。
- **明确范围障碍**：`PostgresQualificationAuthority` 与 `PostgresCandidateGrantResolver` 现在只在 `aearn_rag260_c_*` 隔离数据库授权（`corpus_governance.py:137-146`; `candidate_use_grants.py:20-26`）。D 能规划/测试隔离 PG，不可宣称已能迁移到业务库或公开消费者；解除此门禁属于另经批准的逐 scope 上线/E 安全审计，不要在 D 随手放宽。机器回执已经过期；已有 C 两片段不代表今日 current ready，合成重新签发的 fixture 只证明逻辑不证明真实来源。
